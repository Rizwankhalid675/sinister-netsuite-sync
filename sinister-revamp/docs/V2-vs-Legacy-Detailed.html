1Executive summary

The Legacy storefront was built page-by-page. Each template carried its own copy-pasted markup and inline styling, and several values (support phone, "latest blog" cards) were hardcoded into the markup at build time. It works, but it is inconsistent, hard to change, and easy to break.

V2 rebuilds the same store on a single shared design system (css/sd2-global.css), a library of reusable canonical components, and real store data pulled from Miva tokens instead of duplicated code and baked-in values. The commerce engine — Miva Merchant — is unchanged; only the visible frontend is redesigned. The result is a storefront that is more consistent, far easier to maintain, more trustworthy in the content it shows, lower-risk on third-party dependencies, and enriched with a premium motion/interaction layer the Legacy site does not have.

2What "V2" actually is

Sinister Diesel's storefront runs on Miva Merchant. Miva stays the commerce engine — products, categories, basket, checkout, accounts, orders, URLs, SEO, search, MVT templating, forms, APIs, analytics, and integrations all keep working. Only the visible frontend is being redesigned.

  • V2 = the new frontend. Legacy = the existing live frontend.
  • Legacy is never deleted and never modified by V2 work.
  • V2 templates/partials are created inactive — a file goes live only when a human manually assigns it to a copied test page in Miva Admin and reviews it.
  • Creative direction is a premium performance garage / motorsport engineering / American manufacturing / automotive-tech brand — deliberately not a generic Shopify/WooCommerce/Bootstrap/ReadyTheme catalog.
Naming convention
Legacy: plain names (sfnt.mvt, srch.mvt, bask.mvt). · V2 staging: -v2 suffix (sfnt-v2.mvt, ctgy-v2.mvt). · V2 components: sd2-v2-* prefix. · CSS classes .sd2-v2-*, tokens --sd2-*, JS hooks data-v2-*.

4Architecture: Legacy vs. V2

Legacy pattern

  • Built page-by-page over time
  • Per-template inline / duplicated CSS
  • Copy-pasted markup blocks per page
  • Some values hardcoded at build time
  • Styling drifts between pages
  • One change = edit many files
  • No shared motion/interaction system

V2 pattern

  • One global design system (sd2-global.css)
  • All styling from --sd2-* tokens
  • Reusable canonical partials
  • Real store/blog data with fallbacks
  • Consistent by construction
  • One change propagates everywhere
  • Shared progressive-enhancement JS + motion

The repository is exported/synced Miva theme content (no build system or package manager). Key locations: templates/ (~1280 .mvt), partials/ (V2 components), css/sd2-global.css (the single design system), js/sd2-v2-components.js (shared JS), and the governing V2_CONSTITUTION.md / V2_STRUCTURE.md.

5The V2 design system in depth

There is one design system, in a single file: css/sd2-global.css.

  • Token-driven. All colors, spacing, radius, shadow, typography, and motion are defined as --sd2-* tokens. No duplicated tokens or component CSS may exist in templates, partials, or inline.
  • Layered structure. Organized tokens → layout → components → commerce → listing → search → PDP.
  • Token discipline. CSS references --sd2-* tokens rather than hardcoded values, so a single edit restyles the whole site.

This is the core structural difference from Legacy: change a spacing or color token once, and every V2 component updates — versus hunting through duplicated inline CSS across many Legacy templates.

7JavaScript & interaction layer

Shared progressive-enhancement JS lives in js/sd2-v2-components.js with no external dependencies. Its rules make the frontend resilient and consistent:

  • Modules initialize only when their root hook (data-v2-*) exists — they fail closed when a component is absent.
  • All localStorage access is wrapped in try/catch to tolerate unavailable storage. Fixed keys never renamed: sd2v2_garage, sd2v2_recent_searches, sd2_v2_recent_searches.
  • Component partials contain no inline scripts or styles.
  • Garage toggles are delegated so account/cart/PDP controls all open the same canonical Garage component.
  • Gallery switching, counters, thumbnail keyboard nav, and zoom are centralized in one gallery module.
  • Reduced-motion branches are required everywhere motion is added: count-up, hover/motion, skeleton shimmer, filters, media, sticky buy, PDP tabs, cart progress, and drawer/sheet transitions.

On top of this, V2 adds a premium 3D / motion interaction layer (tilt/parallax, considered transitions) that gives a more modern feel than Legacy's static pages.

8Real data vs. hardcoded values

A concrete Legacy weakness was baked-in content. V2 replaced these with live tokens:

  • Support phone number — was hardcoded into footer markup; now reads the dynamic store-config token, matching the header's source.
  • "Latest From The Blog" cards — were rendering placeholder/dummy content (a generic "NEWS" token); now source real blog-post fields with a graceful fallback if unreachable.
  • Link targets — every nav / footer / help-center link verified against real template files and real Miva &mvte:urls:…auto; tokens; no guessed or broken URLs.

10Third-party / dependency risk

SearchSpring — confirmed INACTIVE
The SearchSpring third-party search/merchandising integration was still referenced in the global <head> but is fully inert. Confirming this de-risks the pending subscription cancellation — but per governance it was flagged, not removed, without sign-off.
Pre-existing risk — spons.mvt
templates/spons.mvt contains a hardcoded monday.com API token in client-side JS. This is a pre-existing live-credential exposure (not introduced by V2) and was left untouched per the "restyle only, don't touch API/token logic" rule. It needs manual rotation in monday.com settings.

12Why V2 is better — reasoned

  1. Consistent by construction — shared tokens mean the whole site looks and behaves the same way. Inconsistency can't creep in per page because there is no per-page styling to drift.
  2. Dramatically easier to maintain — one change to a token or partial propagates everywhere, instead of editing many duplicated Legacy templates and risking missed spots.
  3. More trustworthy content — real store/blog data replaces hardcoded and dummy values, so the site stays accurate as the business changes, with graceful fallbacks when a source is unreachable.
  4. Lower risk — link targets verified against real templates/tokens, and the cancelled SearchSpring dependency confirmed inert before any removal.
  5. More resilient frontend — dependency-free JS that fails closed, guards localStorage, and centralizes gallery/garage logic reduces breakage surface.
  6. More accessible & modern — required reduced-motion branches plus a premium 3D/motion layer deliver a more inclusive and more premium experience than static Legacy pages.

13Migration approach & safety

V2 follows a strict, milestone-based process (M0–M9): Creative exploration → Foundation → Global Components → Homepage → Category/Listing → Search → PDP → Cart/Checkout → Dashboard → Final Polish. Work proceeds one milestone at a time — no skipping, no rebuilding completed milestones.

Hard activation rules
  • V2 is built inactive; creating/editing a file never puts it live.
  • Never overwrite or activate sfnt.mvt, srch.mvt, prod-product_display.mvt, or live header/footer/checkout/basket/account templates with V2 files.
  • Legacy templates are never deleted. One design system only. No inline scripts/styles in partials.

Two batches of live templates were restyled in place to the V2 shell (account/order templates and static content / help pages) — an intentional exception documented in V2_STRUCTURE.md.

V2 is a real improvement in foundation, but it is not finished:

  • V2 templates are not activated yet — Milestones M3–M9 (Homepage, Category/Listing, Search, PDP, Cart/Checkout, Dashboard, Final Polish) not started.
  • Many partials contain [Placeholder] content not yet wired to live Miva arrays: homepage media, search suggestions/guides/no-results, financing/warranty/delivery/rating/gallery, PDP gallery/video/specs/reviews/related/bundles, cart recommendations/shipping/coupon/tax/review, dashboard order rows/tracking/invoices/timeline/addresses/returns/settings, and CTGY product-array wiring.
  • Blog footer card images are still placeholder graphics (content/photo gap, not a code bug).
  • prod-product_display-v2-test.mvt has real Miva wiring only for name/price/image/description/add-to-cart; breadcrumbs, extra media, video, spec fields, reviews, related products, and bundles remain placeholders.
  • No human browser/visual QA yet — fixes are template/code-level verified only. Manual review of the staging URL is required before sign-off.
